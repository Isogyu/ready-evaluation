# 追加実験 v4 の仮説と判定基準 ― 実行前に固定

作成：2026-11-23（v4 の API 実行前）。本書の SHA-256 を `results_v4/run_meta.json` に記録する。実行後の記述は末尾の「実行後の追記」節にだけ書く。

## 背景と問い

v3 では、同じモデルの中で信号を工夫しても誤り検出の性能（AUROC）は上がらなかった。同じプロンプトの繰り返しは97〜99%同じ答えを返し（一致度が機能しない）、同じモデルによる聞き直し（自己検証）は自己申告と同じ情報しか持たなかった。

v4 では、**情報源を別のモデルに変える。** 予測は引き続き固定し（正答率は構造上同じ）、次の2つを振り分け信号に加える。

1. **別モデルによる検証**：あるモデルの予測ラベルを、別のモデルに「正しい確率」で評価させる。
2. **他モデルとの一致**：同じ問い合わせに対する他の2モデルの予測が、元の予測と一致するか。他モデルの予測は分類として取得するので、追加の検証呼び出しは要らない。

## データ

- dev：v2・v3 と同じ500件（3モデルの予測は取得済み）。
- test：BANKING77 の test から新たに500件を層別抽出する。v1・v2・v3 の test（計1,200件）とは重複させない。シード 20261126。
- モデル・プロンプト・生成設定は v1〜v3 と同じ。検証のプロンプトは v3 の自己検証と同じもの（`prompt.verify_system_prompt`）を、別のモデルに対して使う。

## 振り分け信号（すべて事前に定義し、データを見て調整しない）

対象モデルを T とする。

| 記号 | 名前 | 定義 | 追加の呼び出し |
|---|---|---|---|
| S_self | 自己申告 | T が分類と同時に申告した確信度（v1〜v3 と同じ） | なし |
| S_xver(V) | 別モデル検証 | 検証モデル V（T 以外）が、T の予測ラベルの正しい確率を答えた値 | V で1回 |
| S_xagree | 他モデル一致 | T 以外の2モデルの予測のうち、T の予測と同じものの割合（0, 0.5, 1） | なし（各モデルの分類を流用） |
| S_combx | 組み合わせ | (S_self + S_xver(強) + S_xagree) / 3。「強」は Sonnet・Haiku に対しては Opus、Opus に対しては Sonnet | 検証1回 |

- 検証は、各モデルが他の2モデルを検証する6通りすべてを行う（Opus→Sonnet、Opus→Haiku、Sonnet→Opus、Sonnet→Haiku、Haiku→Opus、Haiku→Sonnet）。
- 失敗の扱い：検証が失敗したら確率0、他モデルの分類が失敗したら不一致として数える。T の元の分類が失敗したケースは誤答・全信号0（v1〜v3 と同じ）。

## 仮説と判定基準

主分析の条件：目標信頼性 Y=0.90、a_h=1.00、δ=0.05。区間はブートストラップによる95%区間（しきい値選定込みは1,000回）。判定は「支持」「不支持」「判定保留」のいずれか。

### H1　強いモデルによる検証は、自己申告より誤りをよく見分ける
**対象**：Opus が検証した Sonnet と Haiku の予測。
**判定**：両方で AUROC(S_xver(Opus)) − AUROC(S_self) の95%区間が0より大きければ支持。どちらかが0未満側に有意なら不支持。それ以外は判定保留。

### H2　他モデルとの一致は、自己申告より誤りをよく見分ける
**判定**：3モデルすべてで AUROC(S_xagree) − AUROC(S_self) の95%区間が0より大きければ支持。1モデルでも0未満側に有意なら不支持。それ以外は判定保留。

### H3（主仮説）　正答率が同じでも、別モデルの情報を加えると必要レビュー率が下がる
**判定**：3モデルすべてで、しきい値選定込みブートストラップによる差（S_combx − S_self）の95%区間が0未満なら支持。1モデルでも0より大きい側に有意なら不支持。それ以外は判定保留。少なくとも1モデルで95%区間が0未満なら、「正答率が同じで必要レビュー率が違う例がある」という弱い形の主張が成り立つとして、別に記す。

### H4　検証モデルが強いほど検証の性能が高い
**比較**：(a) Haiku の予測について、Opus による検証と Sonnet による検証。(b) Opus の予測について、Sonnet による検証と Haiku による検証。
**判定**：(a) の AUROC(Opus 検証) − AUROC(Sonnet 検証) と、(b) の AUROC(Sonnet 検証) − AUROC(Haiku 検証) の95%区間が、どちらも0より大きければ支持。どちらかが0未満側に有意なら不支持。それ以外は判定保留。

### H5　別モデルの情報を加える費用は、減るレビュー費用で回収できる
**判定**：3モデルすべてで、1件当たり総コストの差（S_combx − S_self、検証の API 実費を含む、既定条件：4,000円/時・2分）の点推定が負なら支持。1モデルでも正なら不支持。区間（レビュー率の差の区間 × 1件当たりレビュー費用 ＋ 追加 API 費用）が0をまたぐ場合はその旨を記す。

## 探索的な分析（仮説検証ではない）

- 6通りの検証すべての AUROC と必要レビュー率
- 弱いモデルが強いモデルを検証する場合（Haiku→Opus）の性能
- S_xagree・S_xver 単独での必要レビュー率
- 目標85%・95%、a_h=0.90・0.95 での結果
- 下限法・δ法の比較（v3 と同じ方法）

| 仮説 | 判定 | 根拠（95%区間） |

H3 の弱い形（事前に定めた「少なくとも1モデルで95%区間が0未満」）は Haiku で成り立った。**同じ予測（正答率 76.2%で同一）のまま、振り分け信号を変えるだけで、目標90%に必要なレビュー率が 48.6% から 24.8% に下がった。**これは「正答率が同じでもレビュー必要量は違いうる」という論文の中心的な主張と整合する、本プロジェクトで初めての事前登録済みの証拠である。

### 解釈についての注記（事前登録外）

1. **他モデル一致が機能しなかった理由**：3モデルの予測が一致したのは test 500件中408件で、そのうち41件（10%）は3モデルとも同じ誤ったラベルを選んでいた。複数のモデルが一致しても、正答率は90%で頭打ちになる。そのため目標90%＋余裕0.05は達成できず、全件レビューになった。誤りがモデル間で相関している（紛らわしいラベルの組で同じように間違える）ことが原因と考えられる。
2. **組み合わせ信号が Opus・Sonnet で伸びなかった理由**：事前に定めた組み合わせには、性能の低い「他モデル一致」が3分の1の重みで入っている。Sonnet では Opus の検証だけを使う方が良く（AUROC 0.921 対 0.883、必要レビュー率 18.6% 対 23.4%）、組み合わせによって薄まった。
3. **弱いモデルによる検証は逆効果**：Opus の予測を Sonnet・Haiku が検証すると、AUROC は自己申告（0.872）より低かった（0.786、0.748）。検証させるなら、対象より強いモデルを使う必要がある。
4. **安いモデル＋強い検証モデルの総コスト**（探索的）：Haiku の予測を Opus が検証する組み合わせは、目標90%で1件当たり 33.3円（検証費用込み）。Opus を単独で自己申告で使う場合（39.5円）より低かった。差の区間は計算していない。
5. **下限法**：v3 と同じく、過剰レビューは減るが、別データでの適格率は 26〜96% にとどまった。特に組み合わせ信号では 30〜51% と低かった。
