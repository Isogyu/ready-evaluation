# 実験方法

本実験は READY 論文の**完全再現ではない**。論文の評価の考え方（目標信頼性を満たすのに必要なレビュー率を、開発データで決めて保留データで検証する）を、問い合わせ分類タスクで小規模に試す予備実験である。

## 1. データ

| 項目 | 内容 |
|---|---|
| データセット | PolyAI/banking77（Hugging Face、CC BY 4.0）。銀行への問い合わせ文を77の意図カテゴリに分類する |
| 元の分割 | train 10,003件、test 3,080件。この分割を維持した |
| 開発用（dev） | train から 100件 |
| 最終評価用（test） | test から 200件。分析では1回だけ評価し、結果を見て設定を変えていない |
| 抽出方法 | 各クラスから ⌊n/77⌋ 件ずつ、余りはランダムに選んだクラスから1件ずつ（dev は 1〜2件/クラス、test は 2〜3件/クラス） |
| 乱数シード | 20261123（`config.yaml`） |
| 抽出結果 | `data/splits.csv`（case_id = 元の split 名＋行番号） |

正解ラベルはモデルに渡していない。

## 2. モデルと生成設定

| キー | モデルID | 応答の model 値 | 入力 $/1M | 出力 $/1M |
|---|---|---|---|---|
| opus-5-5 | claude-opus-5-5 | claude-opus-5-5 | 4.00 | 20.00 |
| sonnet-5-5 | claude-sonnet-5-5 | claude-sonnet-5-5 | 2.00 | 10.00 |
| haiku-5-5 | claude-haiku-5-5 | claude-haiku-5-5 | 0.10 | 0.50 |

- 実行日時：2026-11-23 06:31〜06:35（UTC）。Models API で3モデルの存在を確認してから実行した（`results/available_models.json`）。
- 料金は 2026-11-03 時点の公表値。
- 共通設定：effort = low、max_tokens = 4000、思考はモデル既定（3モデルとも適応的思考が既定で有効）。
- **Temperature は指定していない。** 現行の API バージョンでは temperature などの指定が400エラーになるため。同じ入力でも再実行で出力が変わりうる。
- GPT 系モデルは API キーが無かったため比較に含めていない。

## 3. 入力と出力

- システムプロンプト：77カテゴリ名の一覧と回答形式の指示（`src/ready_eval/prompt.py`、版 v1）。全モデル同一。
- ユーザー入力：問い合わせ文のみ。
- 出力形式：構造化出力（JSON スキーマ）で `{"predicted_label": <77ラベルの enum>, "confidence": <数値>}` に制約した。
- confidence の指示：「predicted_label が正しい確率を 0〜1 で」。校正された確率ではない自己申告値として扱う。
- ラベルは完全一致 → 正規化一致 → 高類似度の近似一致の順で ID に変換する。今回は900件すべて完全一致だった。
- 失敗（不正出力・ラベル不一致・APIエラー・タイムアウト・拒否・出力上限）は status 列に記録し、誤答として分母に残し、確信度0として最優先でレビュー対象にする設計にした。今回の実行では失敗は0件だった。
- 拒否時に別モデルで再実行するフォールバックは使っていない（比較対象が入れ替わるため）。
- システムプロンプトにプロンプトキャッシュを設定した。キャッシュの効き方は並列実行の順序に依存するため、API 費用には「キャッシュなし相当」の値も併記した。

## 4. 指標

| 指標 | 定義 |
|---|---|
| Accuracy | 正解件数 / 全件数（失敗も分母に含む）。95% Wilson 区間 |
| Brier | mean((confidence − 正誤)²) |
| ECE | **10等幅ビン**（[0,0.1), …, [0.9,1.0]）。参考に15ビンも出力 |
| AUROC（誤り検出） | 誤答を正例、1 − confidence をスコアとした ROC AUC。誤答が10件未満なら「不安定」と表示する設定。ブートストラップ95%区間 |
| AURC | リスク・カバレッジ曲線の下側面積。同じ確信度のケースは同時に採用する |
| レビュー率 | レビュー件数 / 全件数 |
| レビュー後の信頼性 | (採用分の正解件数 + a_h × レビュー件数) / 全件数。期待値で計算 |
| レビュー対象のAI正答率 | レビューに回したケースのうちAIが正しかった割合。レビュー後の信頼性とは別に記録 |

a_h（人間レビューの成功率）は**仮定**。初期実験の主仮定は 1.00（人間は必ず正しく直す、理想化）で、0.90・0.95 で感度分析した。レビューした案件は AI の正誤によらず確率 a_h で正しく処理される、というモデルで、論文の Eq.17 と同じ。

## 5. レビュー方針

| 方針 | 内容 |
|---|---|
| A: AI Only | レビューしない |
| B: Full Review | 全件レビュー |
| C: Random | ランダムに抽出してレビュー。レビュー率 0〜100%（5%刻み）、20シード |
| D: Confidence-Based | 確信度が τ 未満のケースをレビュー。τ の候補はデータに現れた確信度の値すべて |

## 6. 目標信頼性に対するしきい値の選定と検証（READY の簡略版）

1. 開発データで、R̂_dev(τ) ≥ Y + δ を満たす τ のうちレビュー率が最小のものを選ぶ。Y ∈ {0.80, 0.85, 0.90, 0.95}、δ ∈ {0, 0.05}（主分析は論文と同じ 0.05）、a_h ∈ {0.90, 0.95, 1.00}。
2. 選んだ τ を固定し、最終評価データに1回だけ適用する。
3. 片側95%下限 = (採用件数/N) × [採用分正答率の Clopper–Pearson 片側下限] + (レビュー件数/N) × a_h。下限 ≥ Y なら「適格」、未満なら「保証できない」。a_h には区間を付けない（論文 §5.5 と同じ扱い）。
4. 開発データで条件を満たす τ が無ければ「達成不能」とする。
5. 参考値として、最終評価データ上で事後的に求めた最小レビュー率（オラクル）も出した。これは選定に使っていない。

論文の正式な Deployment Qualification との違い：対象がエージェントではなく単発の分類であること、ケース数（論文は各375件、本実験は100件と200件）、確信度の取り方、プロセス上の欠陥を評価しないこと。

## 7. 総運用コスト

1件当たり総コスト = API 費用（実測の平均） + レビュー率 × 人件費/60 × レビュー時間（分）

- 既定：人件費 4,000円/時、レビュー 2分/件（1件当たり 133.3円）、1ドル=150円。**すべて例示的な仮定**。
- 感度分析：人件費 2,000/4,000/8,000円、レビュー時間 0.5/1/2/5分。

## 8. 統計

- 正答率：95% Wilson 区間。
- モデル間の正答率差：同じ200問の対応ありデータなので McNemar の正確検定（不一致ペアの二項検定、両側）。3組の比較を Holm 法で補正。差の区間は対応ありブートストラップ（2,000回）。
- レビュー率の不確実性は2種類出した。
  - しきい値固定のブートストラップ（2,000回）：開発データで決めた τ を固定し、最終評価データだけを再標本化。
  - **選定込みのブートストラップ（1,000回）**：開発・最終評価の両方を再標本化し、毎回 τ を選び直す。全モデルに同じ再標本を使うので、モデル間の差を対応ありで比べられる。しきい値選定のばらつきまで含むので、こちらを主に使う。

## 9. 追加実験（v2）

- 目的：v1 で見えた傾向を仮説として実行前に固定し（`docs/hypotheses_v2.md`）、新しいデータで確かめる。
- データ：dev は v1 の dev 100件＋train の残りから層別に400件（計500件）。test は v1 の test 200件と重ならない500件を層別抽出（シード 20261124、`data/splits_v2.csv`）。
- モデル・プロンプト・生成設定は v1 と同じ。ランダム方式のシードは200に増やした。
- 判定：`src/ready_eval/hypotheses.py` が H1〜H6 を基準どおりに判定し、`results_v2/hypotheses.csv` に出力する。
- 探索的分析：安全余裕 δ（0・0.025・0.05）と開発データ件数（100・500件）が選定レビュー率のずれに与える影響（`results_v2/exploratory_margin.csv`）。事前登録外。

## 10. 追加実験（v3）

- 目的：同じ予測のまま振り分け信号だけを変え、正答率が同じでも必要レビュー率が変わるかを確かめる。あわせて、しきい値を開発データ上の片側下限で直接選ぶ方法（下限法）を固定の δ=0.05 と比べる。仮説は `docs/hypotheses_v3.md` に実行前に固定。
- データ：dev は v2 と同じ500件。test は v1・v2 と重ならない500件（シード 20261125、`data/splits_v3.csv`）。
- 信号：自己申告、一致度（同じプロンプトでの追加分類4回のうち元の予測と一致した割合）、自己検証（別の呼び出しで、予測ラベルが正しい確率を答えさせる。プロンプトは `prompt.verify_system_prompt`）、組み合わせ（3つの単純平均）。
- 予測（正誤）は常に元の1回目の分類を使う。追加呼び出しの失敗は、一致度では不一致、自己検証では確率0として扱う設計（今回は失敗0件）。
- 分析では「モデル:信号」を擬似モデルとして既存の分析をそのまま使う（`src/ready_eval/signals.py`）。下限法と δ法の比較は、開発・最終評価の両方を1,000回再標本化して行う。
- しきい値選定は v3 でベクトル化した（総当たり版と結果が一致することをテストで確認）。

## 11. 追加実験（v4）

- 目的：情報源を別モデルに変えた振り分け信号で、同じ予測のまま必要レビュー率が下がるかを確かめる。仮説は `docs/hypotheses_v4.md` に実行前に固定。
- データ：dev は v2・v3 と同じ500件。test は v1〜v3 と重ならない500件（シード 20261126、`data/splits_v4.csv`）。
- 信号：自己申告、別モデル検証（3モデルが互いの予測を検証する6通り。プロンプトは v3 の自己検証と同じ）、他モデル一致（他の2モデルの予測が一致する割合）、組み合わせ（自己申告・強いモデルの検証・他モデル一致の平均。強いモデルは Sonnet・Haiku に対して Opus、Opus に対して Sonnet）。
- 実装：`src/ready_eval/signals_v4.py`。

## 12. 追加実験（v5）

- 目的：運用構成（誰が答え、何で人間に回すか）どうしの1件当たり総コストを比べる。仮説は `docs/hypotheses_v5.md` に実行前に固定。
- 構成：Opus／Sonnet／Haiku の単独（自己申告で振り分け）、Haiku＋Opus 検証（全件）、Haiku＋Opus 検証（Haiku の確信度が開発データの中央値未満の案件だけ）、Sonnet＋Opus 検証（全件）。
- 総コストの区間：開発・最終評価の両方を1,000回再標本化し、毎回すべての構成のしきい値を選び直す（同じ再標本を全構成に使う）。
- 実装：`src/ready_eval/pipelines.py`。

## 13. 再現

`README.md` の手順で再現できる。`results/raw/` に全応答を保存してあり、同じ設定ならキャッシュを使うので、API を呼ばずに分析だけ再実行できる。
