# 限界と今後の課題

## 1. 実験の位置づけに関する限界

1. **READY 論文の再現ではない。** 論文はエージェント（複数ステップの臨床監査）を扱い、本実験は1回の呼び出しで終わる77クラス分類を扱った。論文の数値と本実験の数値は直接比べられない。
2. **タスクが簡単で、構造も単純。** BANKING77 は意図分類で、エージェントの計画・ツール利用・途中の誤りは評価していない。
3. **比較は同じ会社の3モデルだけ。** GPT 系は API キーが無く含めていない。

## 2. 標本と統計に関する限界

4. **件数が少ない。** v1 は開発100件・最終評価200件（v2 は各500件）。以下の数値は v1 のもの。誤答は最終評価で24〜48件しかなく、AUROC の95%区間は ±5〜6pt、必要レビュー率の区間は（しきい値選定込みで）±15〜20pt 程度ある。
5. **しきい値選定のずれが大きい。** 開発データで選んだしきい値は、最終評価データで事後的に求めた最小値（オラクル）より多くのレビューを選びやすい。v1 の例：Opus 5.5、Y=0.90、a_h=1.00 で、選定結果は29.0%、オラクルは4.0%。追加実験 v2 の探索的分析では、主な原因は件数ではなく安全余裕 δ=0.05 だった（平均 +6〜+18pt の偏り）。δ=0 なら dev 500件でずれはほぼ0になるが、片側下限による保証はほとんど通らない。
6. **クラス別の分析はできない。** 1クラス2〜3件のため。
7. **正答率が近いモデルの組は1組だけ。** v1 では3組とも正答率が有意に異なった。v2 では Opus と Sonnet の差が 2.2pt（有意でない）に縮んだが、この組の目標90%での必要レビュー率の差は判定保留（H3a）。目標85%・95%で見えた差は事前登録外の探索的観察である。また、**目標95%は極端な条件**である。δ=0.05 のとき、開発データ上で信頼性100%（採用分に誤答ゼロ）を求めることになり、開発データで最も確信度の高い誤答1件でしきい値が決まる。
8. **多重比較。** 目標3〜4水準 × a_h 3水準 × δ 2水準の組を多数出している。特定の組だけを取り上げて結論にしないこと。

## 3. 仮定に関する限界

9. **人間のレビューは実測していない。** a_h は 0.90/0.95/1.00 の仮定で、AI の正誤やケースの難しさに関係なく一定とした。実際には、AI が迷ったケースほど人間も間違えやすい可能性がある。
10. **コストは仮定。** 人件費・レビュー時間・為替は例示値。誤答を見逃したときの損失（手戻り・顧客対応）はコストに入れていない。入れると AI Only の評価は大きく変わる。
11. **自己申告の確信度。** 校正された確率ではない。プロンプトの書き方で分布が変わりうる。確信度は限られた値に集中し、最終評価データでの異なる値の数は17〜21種類だった。

## 4. 再現性・妥当性に関する限界

12. **Temperature を指定できない。** 再実行で出力が変わりうる。今回は全応答を保存してあり、分析は再現できるが、API 呼び出しからの再現は完全ではない。再実行によるばらつきは測っていない。
13. **事前学習への混入。** BANKING77 は2020年公開で、モデルの学習データに含まれている可能性がある。正答率が過大になっている可能性を除けない。
14. **ラベル自体の曖昧さ。** 最終評価200件のうち22件は3モデルすべてが誤答した。`wrong_exchange_rate_for_cash_withdrawal` と `exchange_charge`、`beneficiary_not_allowed` と `declined_transfer` など、紛らわしいラベルの組が誤答の上位にある。一部はモデルではなくラベル側の問題の可能性がある（判定は変えていない）。
15. **API 費用はキャッシュの効き方に依存する。** 並列実行の順序でキャッシュ書き込みと読み込みの割合が変わる。キャッシュなし相当の値も出したが、いずれにせよ人件費に比べて2桁以上小さい。

## 5. 追加実験 v3 に固有の限界

- 一致度は、Temperature を指定できない現行 API と effort=low の条件で測った。追加分類は97〜99%が同じ答えになり、信号として機能しなかった。サンプリング条件を変えれば結果は変わりうる。
- 自己検証は同じモデルで行った。別モデルによる検証は試していない。
- 組み合わせ信号の重みは固定の単純平均で、最適化していない。
- 「値が細かいほど必要レビュー率が下がる」という解釈は事前登録外の探索的な説明である。

## 6. 追加実験 v4 に固有の限界

- 主仮説 H3 は判定保留で、事前に定めた基準を満たしたのは「少なくとも1モデル」という弱い形（Haiku）だけである。
- 「安いモデル＋強い検証モデルは強いモデル単独より安い」は探索的な観察で、差の区間は計算していない。
- 検証プロンプトは1種類だけ。検証時に元の確信度や理由を渡す方法などは試していない。
- 今回は検証の費用がレビュー費用に比べて小さかった（1件0.2円程度）。入力が長い業務では、検証の費用が無視できなくなる。

## 7. 追加実験 v5 に固有の限界

- 一部検証の構成は、検証しない案件を「1＋Haiku の確信度」として後回しにする規則を1種類だけ試した。検証した案件と検証しない案件を別々のしきい値で扱う方法などは試していない。
- 総コストの比較は500件では区間が広く（±10円程度）、上位の構成どうしの差を見分けられなかった。
- 検証の費用は、入力が短い分類タスクのため小さかった（1件0.2〜0.3円）。

## 8. 実際の業務エージェントに広げるときの課題

- **成否の判定**：分類のような正解ラベルが無い。成果物の正しさをどう判定するか（人手の採点、検証可能な条件、プロセス上の欠陥の扱い）を先に決める必要がある。
- **確信度の取り方**：エージェントの自己申告、検証器、複数回実行の一致度など、どの信号を使うかで振り分け性能が変わる。
- **途中での介入**：論文も本実験も「完了後に採用かレビューか」だけを扱った。途中で人間に確認する方式は未検証。
- **人間側の実測**：レビュー時間と修正の成功率を、AI が迷ったケースについて実測する必要がある。
- **規模**：目標信頼性を統計的に保証するには、保留データが数百〜千件規模で要る。目標が高いほど必要件数が増える。
- **運用中の監視**：分布が変わったときの再判定の条件。
