## データと条件（v1 から変えるのは件数とデータだけ）

- dev：v1 の dev 100件＋train から新たに400件（v1 dev と重複なし）＝500件。dev はしきい値選定にしか使わないので、v1 の dev を含めてよい。
- test：test から新たに500件（v1 の test 200件と重複なし）。層別抽出、シード 20261124。
- モデル・プロンプト（v1）・effort=low・max_tokens・構造化出力は v1 と同じ。
- 主分析の仮定：a_h = 1.00、δ = 0.05。感度分析：a_h ∈ {0.90, 0.95}、δ = 0。
- 有意水準 α = 0.05（両側）。区間はブートストラップ（選定込みは1,000回、それ以外は2,000回）。

## 仮説と判定基準

各仮説の判定は「支持」「不支持」「判定保留（区間が広く決められない）」のいずれかとする。

### H1　正答率の順序
**仮説**：正答率は Opus > Sonnet > Haiku で、3組とも有意な差がある。
**判定**：3組すべてで差の向きが仮説どおり、かつ McNemar 正確検定の Holm 補正後 p < 0.05 なら支持。向きが逆の組があれば不支持。向きは合うが有意でない組があれば判定保留。

### H2　確信度順レビューの効率
**仮説**：同じレビュー率なら、確信度の低い順にレビューする方式（D）は、ランダムに選ぶ方式（C）より高い信頼性を出す。
**判定**：目標90%（a_h=1.00、δ=0.05）で選んだレビュー率において、3モデルすべてで D の信頼性がランダム方式200シードの97.5パーセンタイルを上回れば支持。1モデルでも下回れば不支持。

### H3　正答率の差は、そのまま必要レビュー率の差にならない（主仮説）
**H3a**：目標90%（a_h=1.00、δ=0.05）で、Opus と Sonnet の必要レビュー率の差は ±10pt 以内である（同等性）。
**判定**：選定込みブートストラップによる差の**90%区間**が [−10pt, +10pt] に収まれば支持（同等）。95%区間が0を含まなければ不支持（差あり）。どちらでもなければ判定保留。

**H3b**：目標95%（a_h=1.00、δ=0.05）では、Haiku は Sonnet・Opus のどちらよりも多くのレビューを要する。
**判定**：Haiku−Sonnet と Haiku−Opus の差の95%区間が、どちらも0より大きければ支持。どちらかが0未満側に有意なら不支持。それ以外は判定保留。

### H4　校正と振り分け能力は一致しない
**H4a**：Opus と Sonnet は確信度を低めに申告する（平均確信度 − 正答率 < 0）。
**判定**：両モデルとも、その差の95%区間の上端が0未満なら支持。

**H4b**：Haiku は Opus より ECE が小さい（校正が良い）が、誤り検出の AUROC は Opus より低い。
**判定**：Haiku−Opus の ECE 差の95%区間が0未満、かつ Opus−Haiku の AUROC 差の95%区間が0より大きければ支持。どちらか一方だけなら判定保留。向きが逆で有意なら不支持。

### H5　総コストはレビュー率で決まる
**仮説**：目標90%（a_h=1.00）の1件当たり総コストに占める API 費用の割合は、感度分析のすべての条件（人件費2,000〜8,000円/時 × レビュー0.5〜5分）・全モデルで5%未満である。API 費用はキャッシュが効かなかった場合の値で計算する（保守的）。
**判定**：すべての条件で5%未満なら支持。レビュー率が0%の条件は除く。

### H6　開発データが少ないと過剰レビューになる
**仮説**：しきい値を dev 100件で選ぶと、dev 500件で選ぶより、test での事後最小レビュー率（オラクル）からのずれが大きく、ばらつきも大きい。
**方法**：dev 500件から100件を非復元で1,000回抽出し、毎回しきい値を選んで test 500件に適用する。比較として dev 500件を復元抽出で1,000回再標本化し、同じ処理をする。目標90%、a_h=1.00、δ=0.05。
**判定**：3モデルすべてで、dev 100件のほうが「選定レビュー率 − オラクル」の平均絶対値と標準偏差の両方が大きければ支持。

### 判定の解釈についての注記（事前登録外）

1. **H6 が不支持になった理由**：δ=0.05 の安全余裕が、件数によらない系統的な過剰レビュー（目標90%で平均 +6〜+18pt）を生んでいた。件数を増やすとばらつきは減るが、この偏りは減らない。δ=0 にすると dev 500件で選んだレビュー率は事後最小値とほぼ一致した（平均絶対ずれ 0〜2pt）。ただし δ=0 では片側下限による適格判定がほとんど通らない（適格率 0〜7%）。`results_v2/exploratory_margin.csv`。
2. **H3b と目標95%の解釈**：δ=0.05 のとき、目標95%は開発データ上で信頼性100%（採用分に誤答ゼロ）を求める条件になる。選ばれるしきい値は「開発データで最も確信度の高い誤答」で決まる（Opus 0.85、Sonnet 0.90、Haiku 0.93）。少数の誤答に左右される不安定な条件である。δ=0 では Opus 30.8%、Sonnet 29.4% とほぼ同じになった。
3. **正答率が近い組（探索的）**：Opus と Sonnet の正答率の差は 2.2pt で、Holm 補正後は有意でなかった。この組の必要レビュー率の差は、目標85%で −10.5pt（95%区間 −17.2〜−0.2）、目標90%で −1.5pt（−14.0〜+9.8）、目標95%で −13.6pt（−19.8〜−8.8）だった。目標によって差の有無が変わり、目標95%の差は上の注記2の条件に強く依存する。事前登録した仮説ではないため、探索的な観察として扱う。

### ECE の値の訂正（2026-11-23 追記）

ECE のビン境界の作り方に誤りがあった（`np.linspace` の端点誤差で、確信度 0.3・0.6・0.7 ちょうどの案件が一つ下のビンに入っていた）。修正後の値で作り直した結果、H4b の ECE 差は −0.066（−0.092〜−0.024）から **−0.057（−0.082〜−0.016）** になった。判定（支持）は変わらない。上の表の値は実行時の記録として残す。最新の値は `results_v2/hypotheses.csv`・`results_v2/metrics.csv`。
