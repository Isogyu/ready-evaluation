# 追加実験 v3 の仮説と判定基準 ― 実行前に固定

作成：2026-11-23（v3 の API 実行前）。本書の SHA-256 を `results_v3/run_meta.json` に記録する。実行後の記述は末尾の「実行後の追記」節にだけ書く。

## 背景と問い

v2 では、自己申告の確信度が約20種類の値に集中し、しきい値を1段変えるとレビュー率が10pt以上跳ぶことがあった。また、正答率が近い Opus と Sonnet について、必要レビュー率の差を事前登録した形では示せなかった（H3a 判定保留）。

v3 では、**同じモデル・同じ予測のまま、振り分けに使う信号だけを変える。** 予測が同じなので正答率は構造上まったく同じになり、必要レビュー率の違いはすべて振り分けの違いから来る。これは「正答率が同じでもレビュー必要量に違いは生じるか」という主な研究課題を、モデル間の比較とは別の角度から直接確かめる設計である。

あわせて、v2 で見つかった「保証の代償」（固定の安全余裕 δ=0.05 による過剰レビュー）を減らすしきい値の選び方を試す。

## データ

- dev：v2 の dev 500件をそのまま使う（v1・v2 で予測を取得済み）。
- test：BANKING77 の test から新たに500件を層別抽出する。v1・v2 の test（計700件）とは重複させない。シード 20261125。
- モデル：claude-opus-5-5、claude-sonnet-5-5、claude-haiku-5-5（v1・v2 と同じ設定：effort=low、max_tokens=4000、プロンプト v1）。

## 振り分け信号（すべて事前に定義し、データを見て調整しない）

| 記号 | 名前 | 定義 | 追加の呼び出し |
|---|---|---|---|
| S_self | 自己申告 | v1・v2 と同じ。分類と同時に申告させた確信度 | なし |
| S_cons | 一致度 | 同じプロンプトでさらに4回分類させ、元の予測と同じラベルを返した割合（0, 0.25, 0.5, 0.75, 1） | 4回 |
| S_ver | 自己検証 | 同じモデルに、問い合わせ文と元の予測ラベルを見せ、そのラベルが正しい確率を0〜1で答えさせる（別の呼び出し） | 1回 |
| S_comb | 組み合わせ | (S_self + S_cons + S_ver) / 3。重みは固定で、学習しない | 上の合計5回 |

- 予測（正誤）は常に元の1回目の分類結果を使う。信号だけを入れ替える。
- 追加の呼び出しが失敗した場合：一致度では「不一致」として数え、自己検証では確率0とする。元の分類が失敗したケースは誤答・全信号0のまま（v1・v2 と同じ）。
- Temperature は API 仕様上指定できないため、モデル既定の値でサンプリングされる。4回の分類が完全に同じ出力になる可能性もあり、その場合 S_cons は情報を持たない。それも結果として報告する。

## 仮説と判定基準

主分析の条件：目標信頼性 Y=0.90、人間レビューの成功率 a_h=1.00、安全余裕 δ=0.05（v2 と同じ）。区間はブートストラップによる95%区間（しきい値選定込みは1,000回）。判定は「支持」「不支持」「判定保留」のいずれか。

### H1　組み合わせ信号は、自己申告より誤りをよく見分ける
**判定**：3モデルすべてで、AUROC(S_comb) − AUROC(S_self) の対応ありブートストラップ95%区間が0より大きければ支持。1モデルでも0未満側に有意なら不支持。それ以外は判定保留。

### H2（主仮説）　正答率が同じでも、振り分け信号で必要レビュー率が変わる
**仮説**：S_comb を使うと、S_self より目標90%に必要なレビュー率が下がる。
**判定**：3モデルすべてで、しきい値選定込みブートストラップによる差（S_comb − S_self）の95%区間が0未満なら支持。1モデルでも0より大きい側に有意なら不支持。それ以外は判定保留。少なくとも1モデルで95%区間が0未満なら、「正答率が同じでレビュー率が違う例がある」という弱い形の主張は成り立つとして、その旨を別に記す。

### H3　一致度だけでも自己申告より誤りをよく見分ける
**判定**：3モデルすべてで AUROC(S_cons) − AUROC(S_self) の95%区間が0より大きければ支持。基準は H1 と同じ。

### H4　自己検証は自己申告と同程度である
**仮説**：S_ver の AUROC は S_self と大きくは変わらない（同じモデルが同じ情報で判断するため）。
**判定**：3モデルすべてで、AUROC(S_ver) − AUROC(S_self) の95%区間が [−0.05, +0.05] に収まれば支持（同等）。区間が0をまたがない（有意差がある）モデルがあれば不支持。それ以外は判定保留。

### H5　下限を直接使うしきい値の選び方は、保証を保ったまま過剰レビューを減らす
**方法**：開発データ上で、片側95%下限（採用分の Clopper–Pearson 下限＋レビュー分 a_h）が Y 以上になるしきい値のうち、レビュー率が最小のものを選ぶ（以下「下限法」）。比較対象は固定の δ=0.05。信号は S_self。
**判定**：3モデルすべてで次の2つを満たせば支持。
1. しきい値選定込みブートストラップで、レビュー率の差（下限法 − δ法）の95%区間が0未満。
2. 同じブートストラップで、下限法が最終評価データで適格になる割合が90%以上。

1だけ満たすなら判定保留、1で差が0より大きい側に有意なら不支持。

### H6　信号を良くする費用は、減るレビュー費用で回収できる
**仮説**：S_comb の追加 API 費用（5回分の実費）は、目標90%で減るレビュー費用（既定条件：4,000円/時・2分）より小さい。
**判定**：3モデルすべてで、1件当たり総コストの差（S_comb − S_self）の点推定が負なら支持。1モデルでも正なら不支持。区間（レビュー率の差の区間 × 1件当たりレビュー費用 ＋ 追加 API 費用）が0をまたぐ場合はその旨を記す。

## 探索的な分析（仮説検証ではない）

- S_ver 単独・S_cons 単独での必要レビュー率

### 解釈についての注記（事前登録外）

1. **一致度が機能しなかった理由**：4回の追加分類は 96.9〜98.8% が元と同じラベルを返し、一致度が1になったケースが94〜98%を占めた。Temperature を指定できない現行 API・effort=low の条件では、出力がほぼ決定的になる。一致度で振り分けるには、サンプリングのばらつきを作る手段（プロンプトの言い換え、別モデル）が必要になる。
2. **AUROC は同じなのに、必要レビュー率が下がった理由**：組み合わせ信号の AUROC は自己申告とほぼ同じだったが、値の種類は20種類前後から70〜86種類に増えた。ECE も3モデルとも下がった（0.111→0.056、0.116→0.048、0.054→0.033）。しきい値をきめ細かく置けるようになり、目標をわずかに超えるところで止められるため、段差による過剰レビューが減ったと考えられる（グラフ9）。全体の順位付け（AUROC）よりも、**値の細かさ**が必要レビュー率に効いた可能性がある。
3. **下限法の適格率が低い理由**：下限法は開発データ上の下限がちょうど目標を超えるしきい値を選ぶ。最終評価データは別の標本なので、そこでの下限が目標を超える確率は5〜9割にとどまった。開発データの下限だけでは、別データでの保証にならない。固定の δ=0.05 は保守的な分、適格率95〜99%を保った。
4. **保証の代償の大きさ**：自己申告・目標90%で、事後最小のレビュー率（オラクル）は Opus 1.4%、Sonnet 6.0%、Haiku 29.2% だった。これに対し δ法の選定は 27.4%、24.4%、49.0%。保証のための余裕が、レビュー量の大部分を占めた。
5. **test の標本差**：v3 の test での正答率（Opus 89.2%、Sonnet 86.4%、Haiku 80.8%）は、v2 の test（86.6%、84.4%、73.8%）と比べて、Haiku で7pt高い。どちらも層別抽出の500件で、標本による違いの大きさを示している。
