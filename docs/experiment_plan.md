### 1.1 論文の主張（要旨）

- 能力ベンチマークは「エージェントが単独でできるか」を測る。導入判断に必要なのは「人間＋AIの系が、許容できる監督負荷とコストで、要求信頼性に達するか」である。
- READY は3段階で評価する：(1) ワークフロー評価、(2) 開発データでの監督方針の最適化、(3) 保留データでの **Deployment Qualification**（固定した方針を統計的に適格判定）。

### 1.2 本実験で借用する定義

| 記号 | 定義 | 論文の式 |
|---|---|---|
| c(τ) | 自律カバレッジ = Pr(s ≥ τ) | Eq.14 |
| e(τ) | レビュー率 = 1 − c(τ) | Eq.15 |
| a(τ) | 自律採用分の正答率 = Pr(u=1 \| s ≥ τ) | Eq.16 |
| a_h | レビュー経路の成功率（論文は 0.90 を仮定） | Eq.17 |
| R(τ) | 信頼性 = c·a + (1−c)·a_h | Eq.17–18 |
| C(τ) | コスト = k_m + k_h·e(τ) | Eq.19 |
| しきい値選定 | 開発データで R̂_dev ≥ Y + δ（δ=0.05）を満たす最大カバレッジのτ | Eq.45 |
| 適格判定 | 保留データで片側95%下限（採用分に Clopper–Pearson、a_h は固定値で信頼区間なし）≥ Y | §5.5 |

### 1.3 論文の主要結果（本実験の結果と混同しないこと）

- 題材は CliniCARE-Bench（臨床監査、4値判定）750件、16システム（エージェント実行基盤＋モデル）。dev/qual 各375件の単一分割。
- 自律正答率の差が0.3pt（GPT-5.4 72.8% / Sonnet 5 72.5%）の2系で、Y=0.76 を満たすのに必要なレビュー率は 39.2% 対 29.6%。**両者とも適格**であり、判定が逆転したわけではない（ブログの「opposite deployment verdicts」は論文より強い表現）。
- 自律正答率と AUROC の相関 ρ = −0.12。
- a_h=0.90 のとき、どの方針も信頼性 0.90 を超えなかった。Y=0.85 では全系でレビュー率が90%超。（追記：これは論文のデータで採用分の成功率が a_h を下回っていたことによる観察で、一般的な上限ではない。paper_review.md §3 を参照）
- 金額のコスト値は論文にもブログにも出てこない（レビュー率のみ）。

### 1.4 論文の限界（本実験の位置づけに関係するもの）

- 実証は「完了後に採用かエスカレーションか」を決める設定の、1ワークフローのみ。
- a_h は仮定値で実測していない。全判定が a_h の値に依存する。
- 分布シフト下の保証なし。単一分割。

## 4. 実験手順

1. 各モデルに「問い合わせ文＋77ラベル一覧」を同一プロンプトで与え、構造化出力（`output_config.format`、JSONスキーマ）で `{"predicted_label", "confidence"}` を受け取る。ラベルは enum で制約し、さらに正規化してID変換する。
2. 失敗（不正出力・APIエラー・タイムアウト・拒否）は `status` 列で記録し、**誤答として全件分母に残す**（confidence=0 として最優先でレビュー行き。論文の欠損8件と同じ扱い）。
3. 応答は1件ごとに `results/raw/{model}/{hash}.json` へ保存。キー = hash(モデルID, case_id, プロンプト版, 生成設定)。存在すれば再実行しない。
4. 累積コスト（usage の実トークン×単価）が上限を超えたら停止。

## 5. 分析

| RQ | 指標・方法 |
|---|---|
| RQ1 | モデル別 Accuracy と、誤答検出 AUROC・AURC の関係（3モデルでは相関係数は出さず並べて記述） |
| RQ2 | 信頼度分布、ビン別正答率、Brier、ECE（**10等幅ビン**、併せて15ビンも参考値） |
| RQ3 | Policy C（ランダム、20シード）と D（信頼度順）で、同じレビュー率でのレビュー後正答率を比較 |
| RQ4 | Y ∈ {0.80, 0.85, 0.90, 0.95}、a_h ∈ {0.90, 0.95, 1.00} で必要レビュー率・コスト。dev で τ を決め（δ=0.05 と δ=0 の両方）、test で検証。片側95% 下限（Clopper–Pearson）を計算し、Y を下回れば「保証できない」と書く |
| RQ5 | 1件当たり総コスト = API実費 + レビュー率 × (人件費 × レビュー時間)。既定 4,000円/時・2分/件（**例示的仮定**）。人件費 2,000〜8,000円、時間 0.5〜5分で感度分析。為替は設定ファイルで指定 |

統計：
- 正答率の 95% CI（Wilson）。モデル間の正答率差は同一問題の対応ありデータなので **McNemar 検定（正確版）**。
- レビュー率・信頼性は **ケース単位のブートストラップ**（2,000回）で 95% CI。
- 多重比較は3モデルのペア3組なので Holm 補正。

開発データの使い方：τ・方針の選定は dev のみ。test は1回だけ評価し、結果を見て設定を変えない。

## 6. API費用の見積もり

前提：入力約1,100トークン/件（システム指示＋77ラベル＋問い合わせ。構造化出力のスキーマ込み）、出力は思考トークン込みで約400トークン/件（effort=low の仮定。**最も不確実な項目**）。件数 300件/モデル（dev100＋test200）。

| モデル | 入力 | 出力 | 小計 |
|---|---|---|---|
| Opus 5.5 | 0.33M × $4 = $1.32 | 0.12M × $20 = $2.40 | **$3.72** |
| Sonnet 5.5 | 0.33M × $2 = $0.66 | 0.12M × $10 = $1.20 | **$1.86** |
| Haiku 5.5 | 0.33M × $0.1 = $0.03 | 0.12M × $0.5 = $0.06 | **$0.09** |
| 合計 | | | **約 $5.7（約900円）** |

- 出力が想定の3倍に膨らんでも約 $13。**上限 $15 を config で設定**し、超過時は停止する提案。
- 本番実行前に各モデル5件で試走し、実トークン数から見積もりを更新して報告する（試走費用は約 $0.1）。
- 件数を増やす余地がある（例：test 600件でも約 $17）。不確実性が大きいため、予算が許すなら増量を推奨。

## 7. 実験設計上のリスク

| # | リスク | 影響 | 対策 |
|---|---|---|---|
| 1 | APIキーが無い | 実測不可 | シミュレーションモード。結果はシミュレーション値と明記し、結論を出さない |
| 2 | 天井効果：BANKING77 は上位モデルで正答率9割前後になりうる | 誤答が200件中10〜20件程度になり、AUROC・ECE・下限が不安定 | 誤答数を報告し、不安定な指標はその旨を明記。増量を選択肢として提示 |
| 3 | 正答率が近くならない（Haiku と Opus の差が大きい等） | 中心の問い（正答率が近い場合）に直接答えられない | 加工しない。正答率差を考慮して考察し、近い組（例：Opus と Sonnet）を中心に比較 |
| 4 | 自己申告 confidence が 0.95 などに集中 | しきい値が粗く、レビュー率が段階的に跳ぶ（論文の overshoot と同じ現象） | 同値はランダムに順序付けせず、ビン単位で扱う。分布を図示 |
| 5 | 事前学習への混入 | 正答率が過大 | 限界に記載。除去はできない |
| 6 | 人間レビューの成功率は仮定 | 信頼性・コストはシミュレーション値 | a_h ∈ {0.90, 0.95, 1.00} で感度分析。実測ではないと明記 |
| 7 | Temperature 指定不可・思考あり | 再現性が完全でない | 生のレスポンスを保存し、キャッシュで同一結果を再利用。一部を再実行してばらつきを参考値として測る（予算内なら） |
| 8 | 77クラス・少数標本 | クラス別の偏りは評価不能 | 全体指標に限定 |
| 9 | 同一社モデルのみ（GPTキーが無い場合） | 一般化が狭い | 限界に記載 |
| 10 | ラベルの曖昧さ（BANKING77 には紛らわしいクラス対がある） | 「誤答」の一部はラベル側の問題 | 誤答例を一部抜き出して定性的に確認（判定は変えない） |
| 11 | 論文との違い（エージェントではなく単発分類、dev/test 各375件ではなく100/200件） | 完全再現と誤認される | 全成果物で「予備実験」と明記 |

4. **件数**：dev 100 / test 200 のままか、増量するか。
